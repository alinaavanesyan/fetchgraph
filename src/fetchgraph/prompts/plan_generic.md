### Твоя задача (ЭТАП A)

Сформировать ТОЛЬКО план выборки в виде СТРОГОГО JSON, без пояснений и комментариев.

Формат плана:

```json
{
  "required_context": ["<provider>", "..."],
  "context_plan": [
    {
      "provider": "<name>",
      "mode": "full|slice",
      "selectors": {},
      "max_tokens": 2000
    }
  ],
  "adr_queries": [],
  "constraints": []
}
```

Требования к полям:

- `required_context` — массив имён провайдеров, чьи результаты должны быть гарантированно доступны на шаге синтеза (даже если для них нет явных запросов в `context_plan`).
- `context_plan` — список шагов выборки контекста.
  - `provider` — имя провайдера из списка доступных.
  - `mode` — только `"full"` или `"slice"`.
  - `selectors` — объект с параметрами запроса к провайдеру.
    - Его форма определяется `selectors_schema` выбранного провайдера (если она есть).
    - Если схемы нет — структура должна быть простой и согласованной с описанием и примерами провайдера.
  - `max_tokens` — ориентировочный лимит токенов для текста, который будет возвращён от этого провайдера.
- `adr_queries` — массив дополнительных запросов к внешним системам (если не используются — оставь пустым массивом).
- `constraints` — дополнительные ограничения/решения для следующего шага (если нечего добавить — оставь пустым массивом).

Поле `selectors` ДОЛЖНО:

- соответствовать `selectors_schema` провайдера, если она задана;
- быть минимально сложным (не добавляй вложенные конструкции без необходимости);
- содержать только те поля, которые реально нужны для выполнения запроса.

Для реляционных провайдеров (`relational_*`) в объекте `selectors` для операции `"op": "query"` можно (и желательно) указывать поле `case_sensitivity`. По умолчанию оно считается `false`, и провайдеры выполняют мягкий поиск по строковым полям (без учёта регистра, с обрезкой пробелов и небольшим допуском к неточным совпадениям). Если нужно строгое, чувствительное к регистру сравнение, явно укажи `"case_sensitivity": true`.

### Общие правила планирования

- Используй только перечисленные провайдеры.
- Предпочитай `mode: "slice"` с осмысленными `selectors` вместо `full`, особенно для крупных провайдеров.
- Учитывай `constraints`, `focus_hints` и `goal` — не подтягивай лишний контекст, который не поможет достигнуть цели.
- НЕ генерируй доменный ответ пользователя, только JSON плана.
- Поле `required_context` используй для провайдеров, контекст которых критически важен на следующем шаге, даже если ты не делаешь по ним отдельный запрос.
- Если запрос пользователя однозначно требует табличных/структурированных данных (фильтры, агрегации, связи между сущностями), обязательно включи соответствующий реляционный/табличный провайдер в `required_context` и/или `context_plan`
- Если пользовательский запрос сформулирован на естественном языке
  (поиск по смыслу: "похожие на", "относятся к теме", и т.п.), ОБЯЗАТЕЛЬНО используй семантический поиск:
  либо "op": "semantic_only", либо поле "semantic_clauses" в запросе "op": "query". (Если провайдер это поддерживает)

### 📊 Специальные правила для табличных/реляционных провайдеров

Провайдер считается табличным/реляционным, если в его `capabilities` есть что-то вроде `schema`, `row_query`, `aggregate`, `semantic_search` (или описание явно говорит, что он работает с таблицами/БД).

Для таких провайдеров:

- Почти всегда используй `mode: "slice"`.
- В `selectors` передавай объект с явным указанием типа операции (например, `"op": "schema"`, `"op": "query"`, `"op": "semantic_only"` и т.п. — смотри `selectors_schema` и `examples` этого провайдера).
- Старайся укладывать все нужные фильтры/агрегации в ОДИН связный `selectors` для этого провайдера, а не дробить на множество мелких запросов без необходимости.

Типичные паттерны:

1. **Запрос вида «дай мне все X, которые связаны с Y»**:
   - Выбери реляционный провайдер, который содержит сущность `X` и связь с `Y` (по его схеме/описанию).
   - Сформируй `selectors` с операцией `"query"` (или аналогичной) и корневой сущностью `X`.
   - Укажи нужные `relations` и фильтры/семантические ограничения по `Y` (например, `filters`, `semantic_clauses`), опираясь на `selectors_schema` и примеры провайдера.

2. **Запрос вида «все X, относящиеся к Z, и их количество/статистика»**:
   - Используй операцию `"query"` с:
     - `group_by` по полю/сущности Z;
     - `aggregations` (`count`, `sum`, `avg`, `min`, `max`, `count_distinct` и т.п.).
   - В `select`/результате указывай только те поля, которые есть в схеме провайдера.

Ограничения:

- Не пытайся строить "кросс-провайдерные" джойны в одном запросе:
  - если нужные сущности находятся в разных провайдерах, выбери один наиболее подходящий;
  - сформируй запрос только к нему или разбей задачу на несколько последовательных шагов (несколько элементов `context_plan`).
- Всегда проверяй, что поля, которые ты используешь в фильтрах/группировках/агрегациях, реально описаны в схеме/описании провайдера.
- Никогда не ставь фильтры по алиасам агрегатов (`aggregations.alias`), если провайдер не поддерживает `having`:
  - вместо этого верни агрегированные данные (с `group_by` + `aggregations`) и сделай фильтрацию в этапе синтеза ответа.
  - пример: если нужно `count(order_item_id) > 3`, верни `order_id` и `item_count`, но НЕ добавляй фильтр по `item_count` в `filters`.
