# Feature: Fine-grained Priority Queue Management with Request Cancellation and Strict Token Limiting

## Problem Statement
Обеспечить надежную и эффективную обработку LLM-запросов под нагрузкой, предотвращая зависания, уменьшая tail latency, и обеспечивая возможность отмены запросов для освобождения ресурсов. Внедрить механизм приоритетов для быстрых повторных или системных запросов, а также реализовать полную систему контроля по лимитам токенов, чтобы избежать ошибок из-за превышения лимитов моделей и обеспечить совместимость с существующими API.

## Users / Actors
- Внутренние системы (health-check, warmup)
- Администраторы (управление приоритетами, настройками)
- Разработчики и интеграторы внешних систем (использование API /v1/chat/completions)
- Конечные клиенты, отправляющие запросы на генерацию

## Use Cases
- Внутренний сервис хочет обеспечить приоритетное выполнение критических запросов, чтобы гарантировать их обработку даже при перегрузке.
- Клиент при отмене запроса хочет освободить ресурсы и ускорить очередь.
- Администратор хочет настроить строгие лимиты токенов для предотвращения ошибок со стороны OpenAI‑подобных провайдеров.
- В системе необходимо динамически выявлять и применять минимальный приоритет по умолчанию для неизвестных или неопределенных запросов.

## Proposed Solution

### Affected Components
- `PriorityQueueRepository` — расширить функциональность, встроить поддержку отмены запросов и приоритетного поведения.
- `QueueService` — адаптировать для обработки отмен, приоритетов и возрастных правил.
- `RequestLifecycleManager` — ввести управление статусами accepted, queued, inflight, done, cancelled для запросов.
- `RequestHandler` — реализовать реакцию на отмены, приоритетное размещение, и падение лимитов.

### Data Models
- Используется: `Request` — для хранения информации о запросе, включающей текущий статус, приоритет, токенный лимит, внутренние идентификаторы.
- Требуется новая сущность: `RequestCancellation` — для фиксации отмененных запросов, времени отмены, причины.

### Interfaces
- Public API / функции:
 - `POST /v1/chat/completions` — с поддержкой приоритетов, отмен.
 - `POST /v1/cancel` — запрос на отмену конкретного запроса.
 - `GET /v1/settings` — возвращает текущие настройки и статус.
- События / подписки:
 - `RequestCancelled` — уведомление о отмене.
 - `RequestEnqueued`
 - `RequestInProgress`
 - `RequestCompleted`

### Integration Notes
Изменения требуют внедрения механизма идентификации запросов (trace_id, request_id), а также корректной синхронизации с существующими кэшами и провайдерами. Внимание к возможным race conditions при отменах и обработке возрастных правил. Необходимо обеспечить полную трассируемость и логирование событий.

## Правила и инварианты

- При отмене запрос должен быть сразу убран из очереди и сфабрикован оканчивающийся статус.
- Запросы с неизвестным приоритетом по умолчанию получают минимальный приоритет или `p2`, конфигурируемо.
- Количество одновременных inflight-запросов по приоритетам не превышает заданных лимитов.
- Все действия в очереди логируются, а метрики своевременно обновляются.

## ADRs
- Использование стандартных API-дизайнов REST для управления отменами и настройками.
- Внедрение глобальных лимитов и правил через систему конфигурации и мониторинга.
- Механизм идентификации запросов и отмены реализуется через trace_id и уникальные идентификаторы.

## Non-Goals / Out of Scope
- Реализация динамического изменения настроек в режиме реального времени.
- Внедрение пользовательских API для ручного управления приоритетами или лимитами.
- Мониторинг и аналитика вне базовых метрик и логов.
